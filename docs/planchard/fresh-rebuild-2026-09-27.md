## Evidence rule

The user's requirement is to create each model **from a blank document in desktop Chrome's dark theme**, using the visible app workflow. Do not import an older model, clone an older library part, inject a document, or count a script-only fixture as a newly authored model. Code and automated tests can close app gaps, but are not a substitute for browser authoring.

Evidence labels in this document:

| Label | Meaning |
|---|---|
| **Fresh UI** | Authored in the current Chrome session from a blank document, with the indicated checks actually performed. |
| **Code only** | A matching tool or implementation exists; the complete book sequence has not been demonstrated on a fresh model. |
| **Pending** | The book's output has not been recreated and accepted in this fresh run. |
| **Gap** | A required behavior is missing, incomplete, or unproved at a known blocking step. |

The `artifacts/planchard/fresh-library-*.json` files are **browser-exported checkpoints** of the new documents, not starting geometry. Older `Planchard *`, `HOUSING`, or `HOUSING_v2` library entries recorded in the 2026-09-13 to 2026-09-23 notes remain historical only.

Concurrent Chrome tabs exposed a library persistence fault during this run: an older tab save could replace the whole IndexedDB library and make another tab's freshly saved model appear only in the disk backup. The keyed per-model persistence and tab refresh paths have been corrected and focused-tested; tabs opened before that code change still need a safe reload. Separate browser exports currently preserve the BULB branch (`fresh-library-2026-09-27-bulb-base-checkpoint.json`) and O-RING/SWITCH branch (`fresh-library-2026-09-27-oring-switch-final.json`) until the active tabs finish and their final records are reconciled.

## Acceptance protocol for each new output

1. Create it from a **blank** document in real desktop Chrome, dark theme, at `http://localhost:8765/`. Keep the browser interaction as the authoring record; scripts may inspect exported results and run code tests.
2. Match the book's driving dimensions. Check overall bounds within 0.01 mm where a value is given; record exact volume and mass when material/density is specified.
3. Edit one upstream driving value and confirm dependent features, mates or drawings update correctly. Undo/redo, save, reload and reopen; check the same history count and a clean exact rebuild.
4. Test the downstream use the book actually requires: part into assembly, assembly into drawing, or exact export into a reader/slicer.
5. Record measured time/clicks, browser-exported checkpoint path, tested code revision, and any deviation. Do not call a whole chapter complete because its primary example merely looks right.
